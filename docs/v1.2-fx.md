# V1.2: FX universes

Status: implemented locally on branch `v1.1-universe` (not committed).
Sources were researched and measured on **2026-09-26, a Saturday**, so the
reference rates here are Friday's, and H.10's are from the week before.

Goal: add FX to the one normalized API with two curated universes,
`fx-major` and `fx-southeast-asia`. The quote model, aggregation methods,
provenance and canonical-id rules stay as they are.

## 1. Model (migration 0014)

| Concept | Representation |
| --- | --- |
| Currency (USD, IDR, …) | existing `currencies` node, with its ISO 4217 code as an identifier and its name as an alias. 18 are modeled: USD and EUR from V1, plus 16 new. |
| FX market (`EUR/USD`) | an **instrument** of class `fx`, with `base_currency_id` and `quote_currency_id`. Price = quote-currency units per 1 base unit. |
| Pair orientation | `UNIQUE (base, quote)`, and the builder refuses a pair whose inverse is already listed. `USD/EUR` is a different market, never a relabelled `EUR/USD`. |

- Currencies are not modeled as instruments. Only the market is one.
- A pair that belongs to both universes is one instrument (`USD/SGD`).
- An FX feed is always priced in its pair's quote currency. The curated
  normalizer enforces this, and so does the API contract (`quoteCurrency.id
  == unit.id`).
- **V1 EUR/USD changed its subject.** It was the EUR currency priced in
  USD. It is now the FX instrument EUR/USD, with a pinned id in
  `data/demo/universe.json`, and Kraken's `ZEURZUSD` feed points to it.
  Migration 0014 withdraws the old currency-subject feed declaration and
  drops currency-subject canonical quotes, which are only a derived cache.
  Old observations are kept as history. The demo's FX check now asserts
  an `fx` instrument with base EUR, quote USD and unit USD, instead of
  "EUR is the subject".

Other schema changes in 0014:

- `quote_feeds.inverted`, `market_observations.inverted`;
- `quote_feeds.freshness_clock` (`continuous` | `weekdays`);
- the two new universe keys.

No new basis or price-type values.

## 2. Build (deterministic)

```text
data/reference/fx-spec.json (Undrly-authored: currencies, pairs, the approved feed per pair, exclusions)
  + data/reference/fx-ids.json (id map: iso4217:CODE, fx:BASE/QUOTE, venue:key)
  → undrly-collect fx build (pure)
  → data/reference/fx.json (curated format) + fx-ids.json + fx-report.md
```

- V1's USD, EUR, Kraken and EUR/USD ids are pinned and reused. The first
  build minted 53 ids; every rebuild mints 0 and is byte-identical. Tests
  check this, and also check that the committed `fx.json` is what the spec
  builds.
- The files are Undrly-authored: they contain symbols and ids, and no
  upstream prices. They are committed, so FX ids are the same on every
  machine.
- `seed` stores the spec as a raw record first, because the universe
  memberships name it. It then ingests `fx.json`. Re-seeding writes 0 facts.
- The equity, crypto, perpetual and commodity ids are unchanged. The FX
  build never reads or writes the V1.1 id map.

## 3. Sources

| Source id | What | Semantics | Bid/ask | Time | Cadence | Access |
| --- | --- | --- | --- | --- | --- | --- |
| `kraken` (existing) | EUR/USD, GBP/USD, USD/CAD, USD/CHF, AUD/USD, EUR/CHF, EUR/GBP | **venue** order book, last trade | yes (book) | none stated → receipt time | continuous, polled 10 s | public |
| `bitstamp` | EUR/USD, GBP/USD | **venue** order book, mid of best bid/ask | yes (book) | ticker `timestamp` (s) | continuous, polled 10 s | public |
| `ecb` | EUR/JPY, EUR/AUD, EUR/CAD, EUR/NZD, EUR/SGD | **reference** rate (concertation around 14:10 CET) | no | date → 00:00 UTC | TARGET working days, around 16:00 CET | public XML |
| `bank-of-canada` | EUR/CAD, GBP/CAD, AUD/CAD, NZD/CAD, CAD/JPY*, CAD/CHF* | **reference** "indicative" daily average | no | date → 00:00 UTC | business days by 16:30 ET | public JSON (Valet) |
| `fed-h10` | USD/JPY, NZD/USD, USD/SGD, USD/MYR, USD/THB | **reference**: official noon buying rates (FRBNY) | no | date → 00:00 UTC | **weekly** release of daily values | public CSV (Data Download Program) |
| `bank-indonesia` | USD/IDR (JISDOR), SGD/IDR, MYR/IDR (middle of BI transaction rates) | **reference**, official | no (BI's own buy/sell rates are not exposed) | stated date, +07:00 | business days (JISDOR around 10:00 WIB) | public XML web service |
| `bnm` | USD/MYR, SGD/MYR | **reference**: interbank middle rate, 17:00 MYT session | no (buying/selling rates are not exposed) | date + session, +08:00 | business days | public JSON (Open API) |
| `cbm` | USD/MMK | **reference**, official | no | stated Unix time | business days | public JSON |

\* Inverted: the source publishes JPY/CAD and CHF/CAD, so the feed is
declared `inverted`. Ingestion computes the canonical `1 / rate` with exact
decimal division, rounded half to even to the source's own significant
digits (inverting cannot add precision: `0.008990` gives `111.2`). A quote's
bid and ask would swap sides (`bid = 1/ask`). The observation records
`inverted = true`, and the raw record keeps the source's own value. There
is no silent relabelling.

A source's "per 100 units" rate (BNM, Bank Indonesia) is divided by the unit
count, exactly. That is normalization, not inversion.

**Kraken coverage is curated by liquidity.** Kraken also lists USD/JPY,
EUR/JPY, AUD/JPY, EUR/AUD and EUR/CAD. Over the 24 h before research, those
books had 17–56 trades and spreads of 15–190 bps (USD/JPY: 155.400 /
158.382). Undrly does not use them as the market price. Bitstamp's SGD/USD
book (0 volume, about 1,050 bps) is excluded for the same reason.

**Rejected or unavailable sources:**
- ExchangeRate-API: its terms forbid use "in any product or service that
  offers programmatic or automatic access to exchange rate data".
- BSP: only an undocumented website SharePoint endpoint exists.
- MAS APIMG and Bank of Thailand: both need registered API keys, and none
  is configured. MAS's data.gov.sg copy stops in 2015.
- SBV, NBC and Bank of the Lao PDR: HTML only (NBC also blocks non-browser
  clients).
- TrueFX: returned no data.
- No scraping, browser impersonation or anti-bot workarounds are used.

## 4. Basis and aggregation

No new vocabulary. Each kind of value maps onto existing terms:

| Value | `basis` | `priceType` | bid/ask |
| --- | --- | --- | --- |
| One venue's book (Kraken, Bitstamp) | `venue` (named) | `last` / `mid` | the venue's |
| Two venues' books | `aggregated` (`mean-venue-mid-v1`) | `mid` | mean bid, mean ask |
| Central-bank reference rate | `aggregated` (set by the institution, not a venue) | `reference` | `null` |

`priceType: reference` is what separates a reference rate from a market
quote, as it already does for gold-api and EIA.

- **Never combined.** A pair has either venue feeds or reference feeds,
  never both; the builder refuses a mix. `mean-venue-mid-v1` only admits
  venue quotes that have a bid and ask, so a reference rate could not
  enter it anyway.
- **Two venue feeds:** EUR/USD and GBP/USD use `mean-venue-mid-v1`,
  unchanged: exact decimals, a mean of mids, the mean bid and mean ask, and
  a 30 s window.
- **One venue feed:** `latest-observation-v1`, served as a Kraken venue
  quote.
- **Two reference feeds** (EUR/CAD: ECB and BoC; USD/MYR: BNM and H.10):
  `latest-observation-v1` serves the newer publication. It is never
  averaged. `/v1/quotes` shows both.
- No FX quote is called NBBO, best execution, interbank or "official". A
  canonical quote names neither the provider nor the venue inputs; the
  provenance stays in `canonical_quote_inputs`.

## 5. Freshness policy

`ageMs` is always literal elapsed time. `freshness` is Undrly's policy
verdict.

| Feeds | Window | Clock |
| --- | --- | --- |
| Kraken, Bitstamp FX | 300 s per feed; `mean-venue-mid-v1` keeps its 30 s | continuous. Both venues trade their fiat books around the clock, including weekends (checked on a Saturday). |
| ECB, Bank of Canada, Bank Indonesia, BNM, CBM | 3 days (259,200 s) | **weekdays** |
| Fed H.10 | 8 days (691,200 s) | **weekdays**. Weekly release: the newest value is usually 3–10 days old. |

## 6. Market hours and weekends

- Spot FX trades continuously from Sunday evening to Friday evening (New
  York time) and is closed at weekends.
- Official reference rates are published on business days only.
- Fix: the `weekdays` clock. It is the smallest deterministic change: one
  feed column, no market-state engine and no holiday calendar.
- Its time from `asOf` excludes Saturdays and Sundays (UTC), so a Friday
  rate is not stale on Sunday.
- A missing weekday publication (a holiday or an outage) makes the rate
  stale after 3 weekdays. That is correct: no new rate exists.
- Live venue FX has no special session handling, because those venues'
  books really do trade at weekends.

## 7. 24-hour change

Superseded in V1.3: `/v1/quote` no longer has `change24h`. For live FX
pairs, `/v1/market` states a `rolling_24h` change from the venue's hourly
bars; reference rates have none.

## 8. Resolver

| Query | Resolves to |
| --- | --- |
| `EUR/USD`, `eur/usd` | an FX instrument. Two currency sides name the FX market in exactly that orientation, and only that one: `USD/EUR` is `not_found`. |
| `EURUSD`, `usdidr` | the same instrument, through its compact symbol alias. The build generates the alias only from two known ISO codes. No fuzzy matching. |
| `IDR`, `Indonesian Rupiah` | the currency (ISO identifier, name alias; case-insensitive) |

**Collisions.**
- None of the 18 codes or 37 compact aliases collides with an existing
  crypto, equity, perpetual or commodity symbol in the local V1.1
  snapshot.
- A test covers the case where a crypto symbol equals an ISO code. The
  bare code is then ambiguous in `/v1/resolve`, but `/v1/quote` still
  serves the only priced candidate, as before.

**Unsupported pairs.**
- A pair whose currencies exist but that has no FX instrument (`USD/PHP`)
  is `not_found`.
- A member without a source (`GBP/JPY`) is `no_quote`.
