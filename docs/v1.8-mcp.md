# V1.8 — Agent / MCP financial discovery

Status: local, branch `worldsfair`. Not committed.

## 1. Purpose

Make Undrly directly usable by AI agents and MCP-compatible clients as a
deterministic financial identity and market-data system. An agent starting
from an ambiguous identifier (ticker, pair, ISIN, FIGI, canonical id,
CAIP-2, CAIP-19) can discover what it is, why it resolved, what it is
related to, where it trades or is deployed, what data Undrly has, in which
units, and where each fact came from.

The agent reasons; Undrly provides facts. The MCP server adds no inference,
no embeddings, no fuzzy matching, no ranking, no advice and no writes. It
never creates identity.

## 2. Architecture

```text
            AI agent / MCP client
                     │  stdio (JSON-RPC)
        typescript/apps/mcp  (@undrly/mcp)
          tools · resource · error model · bounds
                     │  UndrlyApi: GET <path> → { status, body }
     typescript/apps/api routes (createApp)   ← the same code as REST
   resolver · explain · graph · quotes · market data
                     │  read-only connections
         PostgreSQL (canonical graph + normalized data)
```

**Decision: the MCP server consumes the API's own routes, not SQL and not
`service.ts` directly.** Phase 0 audit:

- `apps/api/src/service.ts` and `market-data.ts` hold every query (resolve,
  explain, graph, quotes, candles, history, derivatives).
- `apps/api/src/app.ts` holds the request-level rules on top of them:
  resolution → exactly one priced pair (`onePair`), the `limit`/`start`/`end`
  bounds, staleness handling, error codes.

Calling `service.ts` directly would have forced the MCP package to copy the
`app.ts` rules. Instead, `src/api.ts` defines one function type,
`UndrlyApi = (path) => Promise<{ status, body }>`, with two
implementations:

- `inProcessApi(sql)`: `createApp(sql).request(path)`: the Hono app in the
  same process over a read-only pool (`default_transaction_read_only`). No
  HTTP server, one process to run. The default.
- `httpApi(baseUrl)`: `fetch` against a running API (`UNDRLY_API_URL`).

Both run identical code, so an MCP answer is by construction the REST
answer. The MCP package contains no SQL, no resolver and no relationship
logic; it validates arguments, bounds sizes, composes routes, and maps
errors. Every API body is parsed with the `@undrly/contracts` schema before
it is returned, and every tool result is parsed with the tool's output
schema.

One additive API change was needed (§15): `?unit=<canonical id>` on the
quote, quotes, candles, history, market, derivatives and calendar routes,
so one market (subject, unit) is addressable by ids.

## 3. MCP SDK and specification

Sources consulted: the official TypeScript SDK repository
(`github.com/modelcontextprotocol/typescript-sdk`), the 2026-07-28
specification changelog (`modelcontextprotocol.io/specification/2026-07-28`),
and the published packages' own type definitions.

- Packages: `@modelcontextprotocol/server@2.1.0` (runtime) and
  `@modelcontextprotocol/client@2.1.0` (tests and verification only). v2 is
  the SDK's stable line, released with spec 2026-07-28; v1
  (`@modelcontextprotocol/sdk`) is in maintenance. Zod 4 (already the
  contracts' schema library) is its schema layer.
- Protocol versions served: **2026-07-28** (stateless: `server/discover`,
  per-request `_meta`, no `initialize`) and **2025-11-25** (the `initialize`
  handshake most clients still use). `serveStdio(factory)` picks the era
  from the opening message and pins one server instance per connection.
- Cache hints (2026-07-28 `ttlMs`/`cacheScope`): `tools/list`,
  `resources/list`, `server/discover` and the vocabulary resource are
  `public` for one hour; tool results are never cached.

## 4. Transport

stdio (`src/stdio.ts`). stdout carries only MCP messages; diagnostics go to
stderr. The server is stateless: each instance holds only the API function.
Streamable HTTP is not implemented (§16).

## 5. Tool catalog

Nine tools, all annotated `readOnlyHint: true, destructiveHint: false,
idempotentHint: true, openWorldHint: false`, listed in a fixed order.

| Tool | Input | API | Returns |
| --- | --- | --- | --- |
| `search_instruments` | `query`, `limit` 1–20 (10) | `/v1/search` | `SearchResultV1`, first `limit` results. Discovery only |
| `resolve_instrument` | `query` | `/v1/resolve` | `ResolveResultV1` (`resolved` / `ambiguous` / `not_found`) |
| `explain_instrument` | `query` | `/v1/explain` | `ExplainV1`: status, method, per candidate the matched rules, identifiers, relationships with provenance |
| `get_instrument` | `id` (any canonical id) | `/v1/explain` + graph + probes | node, identifiers, and per market (unit) the data available |
| `get_instrument_graph` | `id` (instrument), `relationshipType?`, `direction` (both), `limit` 1–200 (50) | `/v1/instruments/{id}/graph` | root, edges, `edgeCounts`, listings, deployments, markets, `totals`, `truncated` |
| `get_quote` | `query`, `unit?` | `/v1/quote` | `{ quote: QuoteV1 }` |
| `get_markets` | `id` (instrument) | graph + `/v1/quotes` + `/v1/market` per market | listings, markets (unit, status, statistics), feeds per market |
| `get_history` | `query`, `series` candles\|reference, `interval` (1d), `limit` 1–200 (30), `start?`, `end?`, `unit?` | `/v1/candles` or `/v1/history` | `{ series, candles: CandlesV1 }` or `{ series, history: HistoryV1 }` |
| `get_derivatives` | `query`, `unit?` | `/v1/derivatives` + `/v1/explain` | `{ derivatives: DerivativesV1, contract }` |

Why each exists, and what was merged:

- `resolve_instrument` and `explain_instrument` are separate because
  `resolve` is the compact decision and `explain` the audit trail (evidence,
  identifiers, relationships); an agent that only needs the id should not
  pay for the explanation.
- `get_instrument` is not a second explain: it takes only a canonical id
  (never reinterprets text) and adds what explain lacks, the **data
  availability** per market: canonical quote, candle intervals, reference
  history, derivatives context. It omits relationships (those are the
  graph's).
- `get_instrument_graph` is instrument-rooted like the REST graph. For a
  deployment, chain, currency or entity it answers `unsupported` and points
  to `explain_instrument`, which covers any node's one hop.
- `get_markets` is the only tool that separates instrument, listing, market
  and feed, and the only one showing per-feed provenance (source, venue,
  price type, stored source record).
- `get_history` covers both history routes; `series` is explicit so venue
  candles and published reference values are never confused.
- `get_derivatives` returns the perpetual context plus the stored contract
  terms (`DERIVES_FROM`, `DENOMINATED_IN`, `MARGINED_IN`, `SETTLES_IN`,
  `TRADES_ON`), each with provenance, so the V1.4.1 distinction (price unit ≠
  margin ≠ settlement) is explicit, never one "currency".
- Not exposed: universes, calendar and economic calendar (not identity
  discovery; available over REST).

## 6. Tool schemas

Input and output schemas are Zod 4 schemas advertised as JSON Schema
2020-12 in `tools/list`. Outputs reuse the `@undrly/contracts` V1 schemas
(`ExplainV1`, `QuoteV1`, `GraphV1` parts, `CandlesV1`, `HistoryV1`,
`DerivativesV1`, …), so an MCP result is the REST document or a composition
of REST documents. `tools/list` is about 53 KB, almost all output schemas
(inputs ≈ 5 KB); it is cacheable for an hour.

Arguments are validated by the handler, not the SDK: the advertised schema
is the same Zod schema, but a failure becomes a structured
`invalid_query` / `invalid_identifier` result instead of the SDK's
plain-text error. Unknown arguments are rejected.

## 7. Error model

A failure is a tool result with `isError: true` and

```json
{ "error": { "code": "…", "message": "…", "candidates": [/* ambiguous */], "units": [/* ambiguous market */] } }
```

in `structuredContent` (and as JSON text in `content`).

| Code | When | From |
| --- | --- | --- |
| `not_found` | a well-formed query or id matches nothing | API `not_found` |
| `ambiguous` | several candidates; none chosen. `candidates` lists the resolver's; for an instrument priced in several units, `units` lists them (pass one as `unit`) | API `ambiguous` |
| `invalid_query` | bad argument (type, bound, unknown field, timestamp) or unparseable query | validation, API `bad_request` |
| `invalid_identifier` | malformed canonical id, `unit`, or `caip2:`/`caip19:`/`isin:`… query | validation, API `bad_request` on an identifier query |
| `no_data` | the object exists but has no data of this kind | API `no_quote`, `no_data` |
| `unsupported` | the tool does not apply to this kind (graph of a currency) | MCP |
| `internal` | anything unexpected; the message is fixed, details go to stderr | MCP |

`resolve_instrument` and `explain_instrument` report `not_found` and
`ambiguous` as their answer (`status`), exactly as REST; these are results,
not errors. Database errors and stack traces never reach the client
(tested with a failing API).

## 8. Provenance

The MCP server exposes stored provenance as it is and invents none:

- **Canonical:** the node (canonical id, kind, name, class) and its current
  external identifiers are Undrly's identity.
- **Asserted:** every relationship carries `provenance: { sourceId,
  receivedAt }`, the source that asserted it and when Undrly received it
  (explain, graph, `get_derivatives.contract`). Projections (`LISTED_ON`,
  `DEPLOYED_ON`, `TRACKED_BY`) are marked `projected`.
- **Resolution evidence:** explain's `matches` name the rule and the stored
  value (and the alias's source).
- **Market observations:** `get_markets` feeds carry the source id, venue,
  price type, `observedAt`/`receivedAt`, freshness and the stored source
  record (`id`, `key`: the request the collector made). Quotes carry
  `basis`, `venue`, `asOf`, `receivedAt` and the aggregation method.
- No URL citations are fabricated. Raw upstream payloads are never sent.

## 9. Resources

One resource, `undrly://vocabulary` (`application/json`): node categories,
instrument classes, stored relationship rules (type, subject kind, object
kind) and projections, query and identifier forms, resolve methods, match
rules, search ranks, price types, bases, unit kinds, aggregation methods,
candle intervals, market statuses, and the ten invariants of §12. Every
list is a constant from `@undrly/contracts` or the resolver's
`IDENTIFIER_SCHEMES`; nothing is restated by hand.

Rejected: `undrly://schema` (the tool output schemas already carry it) and
`undrly://sources` (no API route lists sources; exposing them would need new
SQL in the MCP layer or a new endpoint: listed as a gap, §17).

## 10. Prompts and the discovery tool

**Prompts: none.** An `identify_financial_object` prompt would only restate
the workflow. The workflow and the invariants are in the server
`instructions` (sent at initialization and in `server/discover`), which
every client receives without asking.

**`discover_financial_object`: not added.** It would be resolve + explain +
get_instrument. Two reasons against:

1. Resolution can be ambiguous. A one-shot tool must then either stop
   (and the agent makes the same second call anyway) or pick a candidate,
   which Undrly must never do.
2. The composition already exists: `explain_instrument(query)` answers
   what/why/relationships for every candidate; `get_instrument(id)` answers
   identifiers and data availability. Two calls, no inference, and each is
   independently useful.

## 11. The four journeys

Verified by `test/journeys.db.test.ts` (fixture database) and
`scripts/mcp.sh` (production data in `undrly_v14`).

**A. Hyperliquid — "What is BTC-PERP?"** `explain_instrument("BTC-PERP")`:
a `perpetual_future`, matched by alias; `DERIVES_FROM` Bitcoin, `TRADES_ON`
Hyperliquid, `DENOMINATED_IN` Tether, `MARGINED_IN` USD Coin, `SETTLES_IN`
USD Coin. `get_instrument` shows one market, unit **USDT**, with quote, 1h/4h/1d
candles and derivatives. `get_quote`: the mark in USDT with the venue book.
`get_derivatives`: mark, index (oracle), funding, open interest in USDT; the
contract terms keep USDC as margin and settlement.

**B. Solana — the USDC mint.** `explain_instrument("caip19:solana:5eykt4Us…/token:EPjF…")`:
a `deployment` matched by `caip19`, `REPRESENTS` USD Coin (asserted by
`circle`), `DEPLOYED_ON` Solana (projected). `resolve_instrument("USDC")` is
the USD Coin instrument, never the deployment; its graph lists the
deployment with its CAIP-19. The bare mint is `not_found`.

**C. Robinhood Chain — the NVIDIA token.** The CAIP-19 deployment
`REPRESENTS` "NVIDIA • Robinhood Token (RHJ Series 1)" (asserted by
`rhj-api`), `DEPLOYED_ON` Robinhood Chain. `isin:JE00BX9C6J83` is that
`tokenized_security`: `ISSUED_BY` Robinhood Assets (Jersey) Limited,
`TRACKS` NVIDIA common stock (asserted by `rhj-final-terms`), no
`TOKENIZES`. NVIDIA common stock stays a distinct `equity` with its own
ISIN, FIGI, Nasdaq listing and issuer; it never carries the token's ISIN.

**D. Tempo — pathUSD.** The CAIP-19 deployment `REPRESENTS` pathUSD
(asserted by `tempo-rpc`), `DEPLOYED_ON` Tempo. pathUSD is a `crypto_asset`
whose only relationship is `TRACKS` US Dollar (a currency). No `ISSUED_BY`:
Undrly has no authoritative issuer identity and the MCP layer does not fill
the gap. pathUSD, USD, USDC and USDT are four distinct objects.

## 12. Semantic invariants

Frozen in `test/journeys.db.test.ts` and stated in `undrly://vocabulary`:

1. A deployment is not the economic asset.
2. A tracker is not the underlying security.
3. A stablecoin or payment asset is not the fiat currency.
4. Price denomination, margin asset and settlement asset are separate.
5. A feed is not an instrument.
6. A listing is not an instrument.
7. Equal symbols do not establish identity.
8. A bare blockchain address does not establish a deployment.
9. A missing issuer remains missing.
10. A missing relationship remains missing.

## 13. Local development

The MCP server reads the database directly (in process); no API server is
needed.

```bash
UNDRLY_DB=undrly_v14 ./scripts/local-db.sh dev.sh      # optional: keep data fresh (collector + API)
UNDRLY_DB=undrly_v14 ./scripts/local-db.sh mcp.sh      # verify the MCP server end to end

# run it by hand (stdio; a client normally starts it)
cd typescript && DATABASE_URL=postgres://… bun run apps/mcp/src/stdio.ts
```

Environment: `DATABASE_URL` (in process, read-only connections) or
`UNDRLY_API_URL` (a running API, e.g. `http://127.0.0.1:8787`);
`UNDRLY_STALE_AFTER_SECONDS` (default 300) as for the API.

Tests: `test/server.test.ts` (fake API: catalog, arguments, errors, bounds,
composition, both eras) and `test/journeys.db.test.ts` (fresh fixture
database, needs `DATABASE_URL` with `CREATEDB`), run by `bun test` and
`bun run test` in `typescript/` (so by `scripts/check.sh`).

## 14. Client configuration

Any MCP client that launches stdio servers. Paths are relative to where
you cloned Undrly; replace them with yours:

```json
{
  "mcpServers": {
    "undrly": {
      "command": "bun",
      "args": ["run", "<path to undrly>/typescript/apps/mcp/src/stdio.ts"],
      "env": { "DATABASE_URL": "postgres://undrly:<password>@127.0.0.1:55432/undrly_v14" }
    }
  }
}
```

Or against a running API: `"env": { "UNDRLY_API_URL": "http://127.0.0.1:8787" }`.

`scripts/mcp.sh` is the reference client: it spawns the server exactly
like this and drives it with the official SDK client in both protocol
eras (initialization, tool listing, resolve, explain, graph, quote,
derivatives, the Solana, Robinhood Chain and Tempo journeys, structured
errors). No LLM is involved.

## 15. Limitations

- Canonical-id pairs are not a query form: `get_quote` selects a market by
  `query` + `unit` (the `?unit=` API addition), not by a pair of ids.
- Candles do not name their venue or source (the V1.3 contract); history is
  the one feed of the canonical quote. MCP reports what the API reports.
- `get_instrument` probes availability per market (up to 10 markets, ≈ 6
  in-process reads each); `get_markets` likewise reads at most 10 markets.
  `marketsTotal` says how many exist.
- `get_quote`'s `quote: false` availability includes a multi-source
  aggregate that is too old to serve.
- Search results carry no identifiers (the search contract has none);
  identifiers come from explain or get_instrument.
- Instrument terms (contract multiplier, unit of measure, FX base/quote)
  appear in quote, resolve (pair) and derivatives subjects, not in
  `get_instrument`.
- The fixture journey tests pin structure; `scripts/mcp.sh` checks
  production data but not freshness (a quote may be stale when the
  collector is not running).
- `tools/list` is large (≈ 53 KB) because outputs are fully typed.

## 16. Future remote MCP deployment

Not built in V1.8. The code is shaped for it:

- `createUndrlyMcpServer(api)` is a pure factory and each instance is
  stateless, which is exactly what the SDK's `createMcpHandler(factory)`
  (Streamable HTTP, one instance per request, 2026-07-28 sessionless) needs.
  The same factory serves both protocol eras.
- Recommended model: a separate `http.ts` entry mounting
  `createMcpHandler` on the existing Hono stack, deployed beside the REST
  API with `httpApi(API_URL)` (or in process with a read-only replica), behind
  OAuth 2.1 bearer auth per the MCP authorization spec
  (`requireBearerAuth`), with Origin/Host validation, per-client rate limits
  and request-size limits. The tools stay read-only; tool results are not
  cached, tool lists are.
- Before exposure: a licensing review of every source (all are
  local/private demo only today) and labelling `/v1/quotes` provenance for
  public use.

## 17. Dashboard-facing API gaps found

- **Market addressing by ids.** A market is (subject, unit) but the query
  language has no id-pair form. `?unit=` (added) covers most needs; a
  `/v1/markets/{subjectId}/{unitId}` resource would be cleaner.
- **Availability summary.** No route says which data exists for an
  instrument; `get_instrument` derives it with several probes. A
  `/v1/instruments/{id}` (or `?include=availability`) would serve the
  dashboard and MCP in one read.
- **Graph size.** `/v1/instruments/{id}/graph` is unbounded (USD Coin: 360
  edges, ~140 KB). It needs `limit`, `type` and `direction` parameters and
  per-type counts, as the MCP tool does client-side.
- **Non-instrument graph.** Deployments, chains, currencies and entities
  have no graph route; only explain shows their one hop.
- **Candle provenance.** `CandlesV1` does not name its venue or source.
- **Sources registry.** No route lists sources (name, kind, licence
  status).
- **Ambiguous market errors** list the resolved node as the candidate, not
  the (subject, unit) markets.
- **Search** has a fixed limit (20) and no kind/class filter.
