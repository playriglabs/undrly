# V1.5: Solana production identity

Status: implemented locally on branch `worldsfair` (not committed). Built on
V1.4 / V1.4.1. No migration: the V1.4 schema (chains, deployments,
`REPRESENTS`, `DEPLOYED_ON`) already had everything this needed.

## 1. Goal

Put the first **authoritative production** blockchain identities into the
chain-neutral deployment model of V1.4, and prove the graph keeps them apart:

```text
                 USD Coin                     (existing V1 instrument, crypto_asset)
                    ▲
                    │ REPRESENTS               asserted by Circle's published address list
                    │
   deployment solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp/token:EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v
                    │
                    │ DEPLOYED_ON              projected from the deployment's chain
                    ▼
               Solana (chain)                  from the cluster's own genesis hash
```

One asset, one chain, deliberately. Undrly is not a Solana indexer.

## 2. Why a deployment is not the economic asset

"USDC" is an obligation of Circle, redeemable one to one for US dollars. The
SPL mint `EPjF…Dt1v` on Solana is one of many places that obligation exists;
the same USDC also exists as ERC-20 contracts on Ethereum, Base and others.
If the mint were the asset:

- every chain would mint a new "USDC", and the asset would fragment;
- a bridged or wrapped copy (a claim on USDC, not USDC) would be
  indistinguishable from Circle's own;
- an address, which means nothing without its chain, would become identity.

So the asset keeps one id (V1's USD Coin), and each chain presence is its own
node that `REPRESENTS` it. `USDC` (the symbol) resolves to the asset; the
CAIP-19 id resolves to the deployment; the bare mint resolves to nothing.

## 4. Solana CAIP-2 identity

| Field | Value |
| --- | --- |
| Category | `chain` (generic; no Solana-specific object) |
| CAIP-2 namespace | `solana` |
| CAIP-2 reference | `5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` (first 32 characters of the genesis hash) |
| Canonical CAIP-2 | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` |
| Display name | `Solana` (display data, from the binding) |
| Authority | the cluster itself, via `getGenesisHash`; the full hash must be a base58 32-byte value |
| Canonical id | generated on first ingestion, found again by CAIP-2 (`chains_one_per_caip2`) |

A response whose genesis hash gives any other CAIP-2 (devnet, testnet, a
misconfigured endpoint) is **rejected before anything is written**
(`IngestError::UnexpectedChain`). Devnet can exist only as its own chain, with
its own CAIP-2.

## 6. Provenance model

```text
official source                     raw record (bytes)             derived facts (same transaction)
POST api.mainnet.solana.com     →   solana-mainnet-rpc #663    →   chain solana:5eyk… (source_record_id = 663)
GET  developers.circle.com/…md  →   circle #664                →   deployment …/token:EPjF… (source_record_id = 664)
                                                                   deployment REPRESENTS USD Coin (edge, source circle, record 664)
                                                                   DEPLOYED_ON Solana (projected from the deployment row)
```

(Record numbers from the local `undrly_v14` run.)

One thing is **not** from an upstream: the binding
`data/reference/onchain.json`, a reviewed, tracked file that says:

1. the chain the Solana source must describe: `solana:5eykt…Kvdp`, called
   "Solana", asked at `https://api.mainnet.solana.com`;
2. that Circle's USDC address list is about Undrly's existing USD Coin
   (`undrly:instrument:01m3…1kj`), and that its row labelled exactly
   `Solana` is that chain, as an SPL `token`.

Why pinned: Undrly's USD Coin has no external identifier that Circle's page
could name (there is no global crypto-asset identifier in scope), and "which
Solana cluster is mainnet" must be a stated expectation the source is
checked against, not whatever an endpoint answers. The binding states **no
address**: the mint comes only from Circle's stored page. Review: changing
the binding is a reviewed change to a tracked file (like the curated
universe).

## 7. Import and refresh

```text
undrly-collect onchain        # sequential: Solana genesis hash, then Circle's page
./scripts/worldsfair.sh       # seed + one pass + onchain + API checks
```

- Each response is stored raw first; the facts derived from it are written in
  the same transaction; a failed fetch writes nothing.
- Re-running is idempotent: the same bytes are the same record, the chain and
  deployment are found by their natural keys, the edge is `Unchanged`.
- **Change detection.** A changed Circle page is a new raw record. If Circle's
  Solana mint changed, the new mint becomes a new deployment representing USD
  Coin, and `onchain` prints `REVIEW:` for every other deployment still
  representing USD Coin on that chain. Nothing is retracted automatically
  (edges are current assertions; retraction needs reconciliation, not yet
  built). A page whose layout changed (no `## Mainnet` section, another
  header, a row without a backticked address, a duplicated label) fails to
  decode and writes nothing.
- The API never calls Circle or Solana.

## 9. Explain

```text
GET /v1/explain?q=USDC
  USD Coin — instrument, crypto_asset — matched alias symbol "USDC" (undrly-curated)

GET /v1/explain?q=caip19:solana:5eyk…/token:EPjF…
  Solana token:EPjF… — deployment — matched identifier caip19 "solana:5eyk…/token:EPjF…"
  identifiers: caip19 solana:5eyk…/token:EPjF…
  REPRESENTS  USD Coin (instrument)   source circle
  DEPLOYED_ON Solana (chain)          projected
```

The `kind` (`instrument` vs `deployment`), the matching rule and the
relationships make the distinction explicit; nothing is inferred from names.

## 10. Graph traversal

- **From USD Coin**: `/v1/instruments/{USD Coin}/graph` lists the deployment
  under `deployments` (`id`, `chain`, `caip19`) and the `REPRESENTS` edge
  (subject: the deployment) with its provenance (`circle`). Same generic code
  as any instrument.
- **From the deployment**: the graph endpoint is instrument-rooted (V1
  contract); the deployment's own relationships (`REPRESENTS` USD Coin with
  provenance, `DEPLOYED_ON` Solana, projected) are served by `/v1/explain`.
  A node-rooted graph endpoint is a possible later addition; it was not
  needed to answer "what is this mint?".

## 11. Pyth research (not integrated)

From Pyth's documentation (docs.pyth.network, read 2026-09-28) and Hermes'
public feed metadata:

1. **What a feed identifies.** "Every price feed has a unique ID, representing
   the specific pair of assets being priced" (e.g. `Crypto.BTC/USD`). It is a
   **provider price stream**: the median of first-party publishers' prices,
   with a confidence interval (publisher disagreement, not volatility),
   published per pair. It is not an instrument and not a venue.
2. **Stability.** IDs are Pyth's identifiers, not global ones: "Price feeds
   also have different IDs in the Stable and Beta channels", and "Pyth Core
   Price Feed IDs are different from Pyth Pro Price Feed IDs". On Solana each
   feed also has derived price-feed accounts (feed id + shard). Pyth Core was
   upgraded on 2026-08-26 (Pythnet retired); Hermes now requires an API key.
3. **Classes.** Feed metadata carries `asset_type` (Crypto, Equity, FX, Metal,
   Rates, Commodities, Energy, with subclasses such as crypto redemption
   rates and indices), `symbol`, `description`, `quote_currency`, and a
   market-hours `schedule`. Two feeds can share a display symbol with
   different meaning: `Equity.US.AAPL/USD` (session hours) and
   `Equity.Index.AAPL/USD` ("24/7").
4. **Feed vs instrument.** A feed is a **reference price of a pair** by one
   provider network: in Undrly terms, a feed whose observations would be
   `basis = aggregated` (Pyth's aggregation, not Undrly's) with a stated
   confidence, for a market (subject, unit), plus a `PRICED_BY` edge from the
   instrument to a feed node.
5. **Deterministic mapping.** Not from Pyth alone. Metadata names the base
   only by symbol and description (equities add `nasdaq_symbol`, a venue
   symbol); there is no ISIN, FIGI, CoinGecko id or mint. Mapping would need a
   reviewed, per-feed binding (feed id → Undrly subject and unit), like the
   Circle binding, never symbol parsing.
6. **Usage.** Hermes requires an API key (since 2026-08-26); terms of use and
   redistribution were not found in the docs reviewed and are unreviewed.
   Pyth Pro is enterprise/keyed.

**Decision:** not integrated in V1.5. Prerequisites: an oracle-feed node
category and `PRICED_BY` rule, a reviewed feed binding format, a reviewed
licence, and a decision on how a confidence interval is served.

## 13. Known limitations

- One chain and one deployment. Circle's page lists USDC on ~35 mainnets;
  EVM chains are out of scope for V1.5.
- The binding maps Circle's row label `Solana` exactly; if Circle renames the
  row, decoding succeeds but the binding fails (nothing written) until it is
  reviewed.
- No retraction: a mint Circle stops listing stays a stored assertion (the
  `REVIEW:` line flags it).
- USD Coin has no `ISSUED_BY` Circle edge (no authoritative Circle entity
  identifier ingested yet).
- The graph endpoint is instrument-rooted; deployments are explained via
  `/v1/explain`.
- No token decimals, supply, or deployment-level prices.
- `solana-mainnet-rpc` and `circle` have `redistribution = unknown`, like
  every source: local/private demo only.
- Hyperliquid candles under the corrected unit need `scripts/history.sh`
  (done for `undrly_v14` in this milestone: 188,675 perpetual bars in Tether,
  2,174 for PURR and HYPE in USD Coin). That run had 7 failed requests,
  unrelated to V1.5: WLFI's 1d candles (one Hyperliquid request) and six Bank
  Negara Malaysia months, which the collector's HTTP client could not reach
  while `curl` could (pre-existing; seen in earlier collection passes too).

## 14. Future Solana coverage

In order of value, each only with an authoritative source:

1. Other Circle chains from the same stored page (EVM chains need `eip155`
   chain nodes from each chain's own identity source).
2. Native SOL: `solana:…/slip44:501` `REPRESENTS` a SOL crypto asset
   (authority: the Solana protocol; no mint).
3. Other issuer-published stablecoins (e.g. Tether's own address page for
   USDT), following the same binding pattern.
4. Oracle feeds (Pyth) as their own node category, bound per feed.
5. Deployment-level markets (a DEX pool of a specific mint), only with a
   market model that keeps them apart from venue markets.

## 16. Perpetual order books (bid/ask on perpetual quotes)

Hyperliquid's `metaAndAssetCtxs` states no bid or ask, so perpetual quotes
had `bid`/`ask` `null`. V1.5 adds each perpetual's order book as a second
feed and attaches its best levels to the mark.

**Source.** `POST https://api.hyperliquid.xyz/info {"type":"l2Book","coin":…}`
(Hyperliquid info endpoint docs): `levels[0]` bids, `levels[1]` asks, best
first, with the venue's `time` in milliseconds; weight 2 per request against
1,200 per minute per IP (rate-limit docs). Each response is stored raw
(source `hyperliquid`, record key `POST … {"type":"l2Book","coin":"BTC"}`).

**Feeds.** Every perpetual has two Hyperliquid feeds: `mark` (unchanged, from
`metaAndAssetCtxs`) and `mid` (the book: `(best bid + best ask) / 2`, exact,
with the best bid and ask and the book's time). Both are in the contract's
denomination (USDT; USDC for PURR and HYPE). Declared by the universe
snapshot (177) and the V1 curated file (BTC).

**Collection.** `run` sweeps every book, one per request, 50 ms apart, the
sweep restarting every 60 s; a sweep of 178 took 43 s (178 records, 273 KB).
Weight ≈ 356 per sweep plus 80 per minute for the marks, well under the limit.
`run --once` sweeps the books just before the marks.

**Method `mark-with-venue-book-v1`** (declared for every perpetual; migration
0020):

1. the price is the latest venue **mark**; without one there is no quote;
2. `bid`/`ask` are the latest **same-venue** book's best levels, if that book
   is within **60 s** of the mark (`MARK_BOOK_MAX_SKEW_SECONDS`); else `null`;
3. `basis = venue`, `priceType = mark`, `asOf` = the mark's time;
   `eligibleObservations` is 1 (mark only) or 2 (mark and book), and both are
   recorded in `canonical_quote_inputs`.

**`bidAskAsOf`.** A sequential sweep means a book can be up to ~60 s older
than the mark. The quote therefore states the book's own time:

```json
{ "priceType": "mark", "price": "83782.0", "bid": "83670.0", "ask": "83671.0",
  "observedAt": null, "bidAskAsOf": "2026-09-28T…", "asOf": "2026-09-28T…",
  "aggregation": { "method": "mark-with-venue-book-v1", "eligibleObservations": 2 } }
```

A mark may lie outside the attached bid/ask (measured on one pass: 131 of
178, because prices moved during the 43 s sweep; fetched back to back, BTC's
mark was inside its book). `bidAskAsOf` makes the age explicit; the spread
is the book's own (`ask − bid`), never estimated.

**Other endpoints.** `/v1/quotes/{perp}` shows both feeds (mark without
bid/ask, book mid with them), each with its raw record. `/v1/derivatives`
is unchanged. Candles are unaffected.

**Not done.** Streaming books (WebSocket `l2Book`) would align book and mark
in time; streaming is out of scope until Phase 8 (AGENT.md §22).
