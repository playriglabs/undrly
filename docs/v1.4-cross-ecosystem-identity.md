# V1.4: cross-ecosystem financial identity

Status: implemented locally on branch `worldsfair` (not committed). Built on
V1.3 (`v1.1-universe` @ `6ffcfa3`). Migration `0018`.

V1.4 is an ontology milestone. It adds no provider, universe or production
data. It makes the graph able to say, without collapsing distinct objects:

```text
                    Bitcoin (crypto_asset)
                       │
            ┌──────────┴───────────┐
   market (Bitcoin, USD)     BTC perpetual (perpetual_future)
            │                      │ DERIVES_FROM → Bitcoin
     Kraken / Coinbase             │ DENOMINATED_IN → Tether (USDT)
                                   │ SETTLES_IN     → USD Coin
                                   │ MARGINED_IN    → USD Coin
                                   │ TRADES_ON      → Hyperliquid

                     USD Coin (crypto_asset)
                       ▲ REPRESENTS
          ┌────────────┼────────────┐
     deployment    deployment    deployment      (each its own node)
     eip155:1      eip155:8453   solana:5eyk…
       │ DEPLOYED_ON (projected)
     chain

       common stock (equity) ◀─TOKENIZES─ share token (tokenized_security)
          │ LISTED_ON Nasdaq                     ▲ REPRESENTS
          │ ISIN                             deployment ─DEPLOYED_ON→ chain
```

The Apple/tokenized example is supported by the model and tests only, with
fixtures. No production chain, address or tokenized security is seeded.

## 1. Problem

The same economic exposure appears as a spot market, a perpetual, a token
contract on several chains, or a tokenized claim on a share. Before V1.4,
Undrly could represent spot markets, perpetuals and their underlyings, but it
had no object for "this asset on that chain", no way to say "this token is a
claim on that share", and no way to ask the resolver why it chose an object.

The risk is collapse: treating USDC as USD, a USDC contract as USDC itself,
a bridged token as the native one, a share token as the share, or two
contracts at the same address on different chains as one thing.

## 2. Existing model (audit)

What the repository already had, verified against migrations 0001–0017,
`undrly-core`, `undrly-store`, the API and the local `undrly_v11` database.

| Concept | Representation | Notes |
| --- | --- | --- |
| Canonical id | `undrly:<category>:<uuidv7>`, `nodes (id, category)` | Generated, never derived. Categories were `entity`, `instrument`, `listing`, `venue`, `currency`. |
| Entity | `entities` (kind `company`) | Issuers. Identified by LEI or CIK. |
| Instrument | `instruments`, class `equity`, `crypto_asset`, `commodity`, `perpetual_future`, `fx` | **A crypto asset is the economic asset** (Bitcoin, USD Coin): there is no separate "asset" object, and none is needed. |
| Currency | `currencies` + ISO 4217 identifier | Fiat only. USDC is an instrument, never a currency. |
| Venue / listing | `venues` (MIC), `listings` (instrument × venue) + `listing_symbols` (venue-scoped, with validity) | `LISTED_ON` is projected from listings, never stored. |
| Market | **not a node**: (subject, unit) | BTC/USD is Bitcoin priced in the USD currency; the perpetual's market is the perpetual priced in the USDC asset. `quote_feeds` declare which source prices which market at which venue. |
| Feed | `quote_feeds` row (source, symbol, subject, unit, venue, price type) | Not a node, never an instrument. `KRAKEN:XXBTZUSD` resolves to the market it prices. |
| Observation | `market_observations`, `canonical_quotes`, `market_bars`, `perp_contexts` | Exact decimals, raw-record provenance. |
| External identifier | `identifiers` (ISIN, FIGI, LEI, MIC, ISO 4217, CIK) with validity; one node per value at a time; conflicts quarantined | Namespace-specific validation. |
| Relationship | `graph_edges`, canonical direction, one row per asserting source, rules in `relationship_rules` | Storable: `ISSUED_BY`, `TRADES_ON`, `DENOMINATED_IN`, `SETTLES_IN`, `DERIVES_FROM`. Named but not storable: `HOLDS`, `TRACKS`, `MEMBER_OF`, `TOKENIZES`, `REPRESENTS`, `PRICED_BY`, `AVAILABLE_ON`, `RELATED_TO`. No `SAME_AS`. |
| Provenance | `source_record_id` on every fact, composite FK to `source_records` | Raw first. |
| Resolver | TypeScript, exact rules only: canonical id, `scheme:value`, `VENUE:SYMBOL` (listing or feed symbol), `BASE/QUOTE`, exact alias; ambiguous → candidates, never a guess | |
| Graph | `/v1/instruments/{id}/graph`: one hop of stored edges both ways, plus listings | |

| Fact | Count | Source |
| --- | --- | --- |
| perpetuals | 178 | `undrly-curated` (BTC) + `undrly-universe` |
| `DERIVES_FROM` underlying | 176 | CoinGecko's Hyperliquid derivatives tickers (crosswalk), never the ticker alone |

## 3. New concepts

| Concept | Kind | Why it is necessary |
| --- | --- | --- |
| `chain` | node category | `AVAILABLE_ON venue \| chain` and contract addresses "scoped to their chain" (AGENT.md §10–11) need a chain node. Identified by its **CAIP-2** chain id. |
| `deployment` | node category | "USDC on Base" must be individually identifiable without being a second USDC. No existing object fits: a listing is (instrument, venue) with a mutable symbol; a deployment is (chain, immutable address). This is AGENT.md's `Token` node, named for what it is so it cannot be confused with the economic asset (a "token"). Identified by its **CAIP-19** asset type. |
| `tokenized_security` | instrument class | A token backed by, or tracking, a security is its own instrument (issuer, rights, identifiers). Classifying it `equity` would collapse it into the share; `crypto_asset` would hide what it refers to. |
| `REPRESENTS` deployment → instrument | relationship rule | The deployment is that instrument on its chain. An edge, not a column, so it carries provenance and can be absent (unknown). |
| `TOKENIZES` instrument → instrument | relationship rule | The subject is a token-form claim on the object, held in custody or escrow: a wrapped or bridged asset, or a share-backed token. |
| `DEPLOYED_ON` | projection | The deployment's chain, from `deployments.chain_id`, like `LISTED_ON` from listings. Never stored. |
| `GET /v1/explain` | endpoint | "What did Undrly think I meant, and why?" |
| graph `deployments`, `markets` | additive keys | Make deployments and (subject, unit) markets traversable. |

Not added, deliberately:

- No `EconomicAsset` object: a `crypto_asset` instrument already is one, and
  fiat stays `currency`.
- No `SAME_AS`, no ecosystem-specific types (`SolanaAsset`, …).
- No `DEPLOYED_ON` or `AVAILABLE_ON` edge: the chain is intrinsic to a
  deployment; an instrument's presence on a chain is a deployment that
  `REPRESENTS` it.
- No `TRACKS` instrument → instrument yet. When a real tracker product is
  integrated, its legal form decides `TOKENIZES` (custodial claim),
  `DERIVES_FROM` (derivative) or a new rule for `TRACKS`.
- No market node, no deployment-level prices, no token `decimals` column
  (added with the first onchain amount).

## 4. Identity boundaries

| Object | Identity | Never identified by |
| --- | --- | --- |
| Economic asset (Bitcoin, USD Coin) | generated instrument id (class `crypto_asset`) | symbol, any deployment's address |
| Fiat currency (USD) | generated currency id; ISO 4217 code as identifier | — |
| Spot market (BTC/USD) | (subject, unit) | a feed symbol |
| Perpetual | generated instrument id | its underlying's id or symbol |
| Chain | generated id; **CAIP-2** `namespace:reference` unique (`chains_one_per_caip2`) | name |
| Deployment | generated id; **(chain, asset namespace, asset reference)** unique (`deployments_one_per_asset`) | address alone, token symbol, token name |
| Tokenized security | generated instrument id; its own identifiers if it has any | the underlying's ISIN/FIGI/listing (an ISIN maps to one node at a time; a second claim is quarantined) |

## 5. Relationship semantics and direction

All stored in canonical direction `dependent → thing it depends on`; the
inverse is derived at query time.

| Type | Subject → object | Meaning | Status |
| --- | --- | --- | --- |
| `ISSUED_BY` | instrument → entity | issuer | reused |
| `TRADES_ON` | instrument → venue | traded at | reused |
| `DENOMINATED_IN` | instrument → currency \| instrument | price unit of the instrument | reused |
| `SETTLES_IN` | instrument → currency \| instrument | the asset cash flows are paid in (delivery or cash settlement; for a perpetual, profit and loss and funding) | reused; meaning made precise in V1.4.1 (§15) |
| `MARGINED_IN` | instrument → currency \| instrument | the asset posted as margin (collateral) | **new rule** (V1.4.1, §15) |
| `DERIVES_FROM` | instrument → instrument | derivative → underlying (inverse label `UNDERLYING_OF`) | reused |
| `TOKENIZES` | instrument → instrument | token-form claim on an asset held in custody or escrow | **new rule** |
| `REPRESENTS` | deployment → instrument | this deployment is that instrument on its chain | **new rule** |
| `LISTED_ON` | listing's instrument → venue | projected from `listings` | reused projection |
| `DEPLOYED_ON` | deployment → chain | projected from `deployments.chain_id` | **new projection** |

Wrapped, bridged and native are distinguishable by structure, not by a flag:

```text
native USDC on Ethereum:  deployment ─REPRESENTS→ USD Coin
bridged USDC on a chain:  deployment ─REPRESENTS→ Bridged USDC ─TOKENIZES→ USD Coin
native ether:             deployment eip155:1/slip44:60 ─REPRESENTS→ Ether
wrapped ether:            deployment eip155:1/erc20:0x… ─REPRESENTS→ Wrapped Ether ─TOKENIZES→ Ether
share token:              deployment ─REPRESENTS→ share token ─TOKENIZES→ common stock
```

A deployment can only represent an instrument: `deployment REPRESENTS
currency` is refused by `relationship_rules`, so a stablecoin contract can
never be recorded as the USD currency.

## 6. Blockchain deployment identity

From the Chain Agnostic standards (read 2026-09-28 at
`github.com/ChainAgnostic/CAIPs` and `ChainAgnostic/namespaces`):

| Standard | Grammar | Undrly rule |
| --- | --- | --- |
| CAIP-2 | `namespace [-a-z0-9]{3,8} : reference [-_a-zA-Z0-9]{1,32}`, case-sensitive | namespaces `eip155` (decimal chain id, no leading zeros) and `solana` (32 base58 characters of the genesis hash); others are rejected until their address rules exist |
| CAIP-19 | `chain_id / asset_namespace [-a-z0-9]{3,8} : asset_reference [-.%a-zA-Z0-9]{1,128}` | `erc20` (EIP-155 chains), `token` (SPL mints on Solana), `slip44` (a chain's native asset, 0 ≤ n < 2³¹) |
| EVM address | `0x[a-fA-F0-9]{40}`; CAIP-10 eip155 profile: accept checksum case and lowercase | stored lowercase; mixed case must be a valid **EIP-55** checksum (Keccak-256, verified in Rust) |
| Solana address | base58 public key | must decode to exactly 32 bytes; case-sensitive, stored exactly |

Enforced by the database, not only by Rust:

- `deployments (chain_id, chain_namespace) → chains (id, caip2_namespace)`:
  a deployment cannot claim a namespace its chain does not have.
- `deployments_asset_namespace_on_chain`: `erc20` only on `eip155`, `token`
  only on `solana`, `slip44` on either.
- `deployments_asset_reference_shape`: lowercase hex for `erc20`, base58 for
  `token`, a decimal for `slip44`.
- `deployments_one_per_asset`: one node per (chain, namespace, reference).

Consequences, each tested: the same EVM address on Ethereum and Base is two
deployments; an address without its chain resolves nothing; a Solana mint
can never be looked up as an EVM address (different namespace and format).

Queries (explicit prefixes, so they never collide with `VENUE:SYMBOL`):

```text
caip2:eip155:8453
caip19:eip155:1/erc20:0x6b175474e89094c44da98b954eedeac495271d0f
caip19:solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp/token:EPjF…
```

`resolve` reports these as method `identifier`. The API lowercases an ERC-20
address before lookup; it does not recheck EIP-55 (it only reads, and stored
addresses were verified when written).

## 7. Hyperliquid validation

No ingestion changed. The existing graph is the proof:

```text
explain BTC-PERP
  resolution  BTC Perpetual (Hyperliquid)   class perpetual_future
  matched     alias symbol "BTC-PERP" (source undrly-curated)
  DERIVES_FROM    Bitcoin        (undrly-curated)
  DENOMINATED_IN  Tether         (undrly-curated, V1.4.1)
  SETTLES_IN      USD Coin       (undrly-curated)
  MARGINED_IN     USD Coin       (undrly-curated, V1.4.1)
  TRADES_ON       Hyperliquid    (undrly-curated)

graph BTC-PERP  markets: [ unit Tether (asset) at Hyperliquid ]
graph Bitcoin   markets: [ unit USD (currency) at Coinbase, Kraken ]
                edges:   BTC Perpetual ─DERIVES_FROM→ Bitcoin   (inverse: UNDERLYING_OF)
```

- BTC spot and the perpetual are different instruments that share an
  underlying through an edge, never through a symbol.
- BTC/USD (a currency unit) and the perpetual's market (the USDT asset)
  are different markets. `BTC/USDC` resolves to a (Bitcoin, USD Coin) pair that
  no feed quotes.
- `kPEPE` keeps `contractMultiplier: "1000"` and `DERIVES_FROM` Pepe.
- **Unresolved (unchanged from V1.1):** `ADA` and `kBONK` have no CoinGecko
  derivatives crosswalk, so no `DERIVES_FROM` edge. Symbol matching would
  link them; it is not used.

The price-unit question this validation raised is resolved in
[§15](#15-hyperliquid-contract-semantics) (V1.4.1).

## 8. Resolver and explain

`GET /v1/explain?q=` (also `/v1/explain/{q}`) calls the **same resolver** as
`/v1/resolve`. The rules were refactored so each one can also report its
evidence; the evidence queries repeat the rule's predicate restricted to the
matched node, and never change which nodes match or their order. `status`
and `method` always equal `/v1/resolve`'s (tested).

Match rules, exactly those the resolver has:

| rule | fires on |
| --- | --- |
| `canonical_id` | an `undrly:…` id of an existing node |
| `identifier` | `scheme:value` (`isin`, `figi`, `lei`, `cik`, `mic`, `iso4217`, `caip2`, `caip19`), or a bare identifier value |
| `alias` | an exact alias, case-insensitive (`symbol` or `name`) |
| `class_share_symbol` | `BRK-B` looked up as the equity symbol `BRK.B` |
| `listing_symbol` | `VENUE:SYMBOL` → a listing's current symbol |
| `feed_symbol` | `VENUE:SYMBOL` or `SOURCE:SYMBOL` → a quote feed's symbol |
| `fx_pair` | `BASE/QUOTE` of two currencies → the FX market in that orientation |

Each candidate also carries its current identifiers, its outgoing edges with
provenance, the projections `LISTED_ON` / `DEPLOYED_ON`, and, for a pair,
whether a feed quotes it. There are no scores or confidence percentages: a
rule matched exactly or it did not. An ambiguous query is explained, never
decided. `quotedPairsOnly` says when the V1.1 pair rule removed unquoted
combinations.

Resolver changes, all additive: `caip2:` and `caip19:` queries; chain and
deployment nodes in search names (discovery only, never identity). Nothing
that resolved before resolves differently.

## 9. Graph

`/v1/instruments/{id}/graph` is unchanged except for two keys, each omitted
when empty so every earlier document is byte-identical:

- `deployments`: `{ id, chain, caip19 }` for each deployment that
  `REPRESENTS` the root.
- `markets`: `{ unit, venues }` for each unit a declared feed prices the
  root in. Units are canonical (`kind` `currency` or `asset`), so USD and
  USDC never merge.

Traversal is generic: nothing in the API knows about a particular chain or
venue. `perp → DERIVES_FROM → Bitcoin → markets` and `USD Coin →
deployments` are the same code path as every other instrument.

## 11. Provenance

- Chains and deployments name the raw record that minted them
  (`source_record_id`, like every node object; covered by the provenance
  coverage test).
- `REPRESENTS` and `TOKENIZES` are ordinary edges: one row per asserting
  source with its record. Contradictory assertions (a deployment said to
  represent two instruments) are stored side by side, as for every edge,
  until reconciliation exists.
- Projections (`LISTED_ON`, `DEPLOYED_ON`) carry the provenance of the row
  they are projected from.

## 13. Known limitations and open decisions

- Hyperliquid perpetual semantics: corrected in V1.4.1 (§15). The
  USDC-denominated exceptions (PURR, HYPE) are a documented list, not an API
  field; it must be re-checked when Hyperliquid changes its specification.
- `ADA` and `kBONK` perpetuals have no underlying edge.
- No production chain, deployment or tokenized security exists yet; only
  test fixtures.
- CAIP-2 namespaces other than `eip155` and `solana`, and asset namespaces
  other than `erc20`, `token`, `slip44` (NFTs, `erc721`), are rejected.
- The API does not verify EIP-55 on read (it lowercases); writes do.
- No deployment-level market data (a DEX pool of one mint), no oracle-feed
  nodes (`PRICED_BY`), no token decimals or raw amounts yet.
- Contradictory `REPRESENTS` assertions are not flagged (no
  reconciliation).
- `graph` stays one hop and instrument-rooted; a deployment or chain is
  described by `/v1/explain`.

## 14. Future ecosystem adapters

Each is an importer that writes chains, deployments and edges through
raw-first ingestion, with an authoritative source per fact. None is
implemented in V1.4.

| Adapter | What it would add | Authority needed |

Hyperliquid's own documentation and API, before any basis calculation or

Key wording (contract specifications):

> Hyperliquid has one main style of margining for perpetual contracts: USDC
> margining, USDT denominated linear contracts. That is, the oracle price is
> denominated in USDT, but the collateral is USDC. [...] Note that no
> conversions with the USDC/USDT exchange rate are applied, so these
> contracts are technically quanto contracts where USDT pnl is denominated
> in USDC.
>
> When the spot asset's primary source of liquidity is USDC denominated, the
> oracle price is denominated in USDC. Currently, the only USDC-denominated
> perpetual contracts are PURR-USD and HYPE-USD [...]

The table also states: "Instrument type: Linear perpetual", "Contract: 1
unit of underlying spot asset", "Delivery / expiration: N/A (funding
payments every hour)".

### Semantics, field by field

| # | Concept | Official semantics | Evidence |
| --- | --- | --- | --- |
| 1 | Underlying | the spot asset ("Hyperliquid oracle index of underlying spot asset"; contract = 1 unit of it) | contract specifications |
| 2 | Price denomination (quote unit) | **USDT**; **USDC** for PURR and HYPE | contract specifications |
| 3 | Oracle price | weighted median of CEX (and, for Hyperliquid-native assets, Hyperliquid) spot mids; "denominated in USDT" (USDC for PURR/HYPE) | contract specifications, oracle |
| 4 | Mark price | median of oracle + EMA(mid − oracle), Hyperliquid book/last trade, and CEX perp mids; the contract's price, so in the denomination (USDT; USDC for PURR/HYPE) | robust price indices, contract specifications |
| 5 | Margin / collateral | **USDC** ("the collateral is USDC"); `metaAndAssetCtxs` states `"collateralToken": 0`, and spot token 0 is `USDC` in `spotMeta` | contract specifications, API |
| 6 | Settlement | no delivery or expiry ("N/A"). Cash flows (profit and loss, funding) are paid to the USDC margin balance without USDC/USDT conversion (quanto) | contract specifications, funding, entry price and pnl |
| 7 | PnL accounting unit | USDC: "USDT pnl is denominated in USDC"; pnl = `side × (mark − entry) × size`, computed in the price denomination and credited 1:1 in USDC | contract specifications, entry price and pnl |
| 8 | Funding payment | `position_size × oracle_price × funding_rate`, hourly, "added or subtracted from the balance"; `userFunding` reports each payment as `usdc` | funding, API |
| 9 | Open interest | `openInterest`: contracts (size units of the market; `k` markets are 1,000 units of the base) | API, existing V1.1 rule |
| 10 | Volume | `dayBaseVlm`: contracts; `dayNtlVlm`: notional = contracts × price, in the price denomination (not converted) | API |

`funding` in `metaAndAssetCtxs` is the hourly rate (a fraction; the funding
page: "paid every hour at one eighth of the computed [8-hour] rate").
`prevDayPx` is a price, in the denomination.

HIP-3 (builder-deployed) perp dexes state their own `collateralToken` and are
not part of Undrly's universe (main markets only).

### Previous Undrly model

| Where | Meant | Correct? |
| --- | --- | --- |
| Mark feed `unit` = USD Coin (all 178), so quotes, observations, perpetual contexts, bars and `/v1/derivatives` `unit` | price unit | **Wrong** for 176 USDT-denominated perpetuals; right for PURR and HYPE |
| `SETTLES_IN` USD Coin (178) | V1 docs: "settles in"; V1.3 contract: "prices are in `unit` (the settlement asset)" | the edge is right (cash flows are paid in USDC); treating the settlement asset as the price unit was the error |
| no `DENOMINATED_IN` | — | missing: the price unit was not stated as a fact |
| no margin fact | — | missing: no vocabulary for collateral |
| `DERIVES_FROM` underlying (176) | underlying | correct |
| `priceType` `mark` | the venue's mark | correct |
| `volume24hNotional` "in the settlement unit, USDC" (provider comment, V1.3 docs) | notional volume | **Wrong**: it is in the denomination |

So there was an actual bug, not only ambiguous naming: every USDT-denominated
perpetual price was served as a USDC price, and the API contract documented
`unit` as the settlement asset. The numbers themselves were never wrong; the
unit attached to them was.

### Mapping now

```text
BTC perpetual ─DERIVES_FROM──▶ Bitcoin
              ─DENOMINATED_IN▶ Tether          (USDT; price unit of mark, oracle, notional)
              ─SETTLES_IN────▶ USD Coin        (profit and loss and funding are paid in USDC)
              ─MARGINED_IN───▶ USD Coin        (collateral)
              ─TRADES_ON─────▶ Hyperliquid
mark feed unit = Tether

HYPE perpetual ─DENOMINATED_IN▶ USD Coin, SETTLES_IN / MARGINED_IN USD Coin, feed unit USD Coin
```

- `MARGINED_IN` (instrument → currency | instrument) is new: no existing type
  meant collateral. `SETTLES_IN` is kept, with its meaning made precise
  ("the asset cash flows are paid in"), because Hyperliquid does pay profit
  and loss and funding in USDC. Margin and settlement are the same asset here,
  but they are different facts and are stored separately.
- The builder asserts `SETTLES_IN` and `MARGINED_IN` only when the stored
  `metaAndAssetCtxs` response says `collateralToken: 0` (the documented USDC
  token); otherwise it records an exclusion and asserts neither.
- The USDC-denominated exceptions are `HYPERLIQUID_USDC_DENOMINATED`
  (`HYPE`, `PURR`) in `undrly-universe`, with the specification quoted. The
  API has no per-market denomination field, so this list is the documented
  fact, and must be revisited if the specification changes.
- BTC's edges and feed live in `data/demo/universe.json` (V1): it now carries
  Tether, `DENOMINATED_IN usdt`, `MARGINED_IN usdc`, and the feed in `usdt`.

### USDT identity

Tether is the existing crypto asset of CoinGecko id `tether` (V1.1 import,
`undrly:instrument:01m3c732qnehv8ex0vnrmngb7v`). V1.4.1 pins that same id in
the V1 curated file (key `usdt`, name `Tether`, aliases `USDT` and `Tether`)
so the V1 demo is self-contained and the V1.1 build reuses it
(`V1_PINS`). No id changed, no node was created, and no deployment was
added. USD (currency, ISO 4217), USD Coin and Tether are three canonical
nodes; no edge, alias or identifier makes any of them another.

### API implications

- `QuoteV1` / `ObservationV1` for a USDT-denominated perpetual: `unit` is
  `{ "kind": "asset", "code": "USDT", "id": <Tether> }`.
- `DerivativesV1.unit` is documented as the **price denomination**
  (previously "the settlement asset"). Mark, index, mid, 24h-ago price and
  notional volume are in it; funding is paid in the settlement asset.
- Graph and explain show `DENOMINATED_IN`, `SETTLES_IN`, `MARGINED_IN`.
- No field was renamed; `unit` now means exactly what the contract says.

### Why USD, USDC and USDT stay distinct

They are different obligations of different issuers (a fiat currency, a
Circle-issued token, a Tether-issued token) with market prices against each
other that are not guaranteed to be 1. Hyperliquid itself relies on this: it
applies "no conversions with the USDC/USDT exchange rate", which is exactly
the difference a quanto contract leaves to the holder.

### Future spot/perp basis (not implemented)

Comparing `BTC/USD` spot (Kraken/Coinbase, unit USD) with the BTC perpetual
(unit USDT) requires, explicitly:

1. **Unit alignment**: a USDT/USD rate with its own source, basis, time and
   freshness (e.g. a venue's USDT/USD book), and the direction of conversion
   stated. Never 1.
2. **Timestamps**: spot `asOf`, perp receipt time (Hyperliquid states none)
   and the conversion rate's time, with a maximum skew.
3. **Which perp price**: mark (what pnl uses) or oracle (what funding uses);
   the oracle is itself a spot index in USDT, so `mark − oracle` is a basis
   within one unit that needs no conversion.
4. **Contract terms**: the contract multiplier (`k` markets) before any
   comparison per unit of the underlying.
5. **Quanto effect**: pnl is paid in USDC without conversion, so a
   cash-flow basis also depends on USDC/USDT, a third rate.

Output would name the method, every input and its unit, and would never be
labelled a price.
